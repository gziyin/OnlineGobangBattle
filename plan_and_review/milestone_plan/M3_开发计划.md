## 二、模块化开发策略

**原则**：实现一个模块 -> 编写测试 -> 测试通过 -> 再进入下一个模块

### 关键设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 认证方案 | **沿用纯 JWT** | 与 M2 保持一致，不重新引入 session |
| 在线状态模型 | **离线 / 大厅空闲 / 匹配中 / 房间中** | 覆盖 M3 最小闭环，便于 M4 扩展 |
| 连接管理 | **双管理器方案** | `OnlineManager` 不暴露 `connection_hdl`，彻底隔离 WebSocket++ 依赖，业务模块只依赖 `online.hpp` |
| 阻塞队列接口 | **仅保留 `timed_pop()`** | 消费线程通过 `is_shutdown()` 区分超时与关闭，不会卡死，`shutdown` 可优雅退出 |
| 匹配策略 | **三段位分桶 + 超时放宽** | 与总项目计划一致，实现复杂度可控 |
| 队列删除策略 | **懒删除** | 取消时打标记，出队时校验，避免并发删除带来的复杂锁竞争 |
| `tier` 字段 | **不存入 `MatchRequest`** | 由 `score_to_tier()` 计算，消除 `score` 与 `tier` 数据不一致风险 |
| WebSocket 鉴权 | **建连后按事件携带 token 校验** | 与现有 HTTP/JWT 体系兼容，改动最小 |
| 心跳处理 | **M3 简单接入，后续可下沉** | 先满足当前联调需要，后续可迁移到连接管理基础设施层 |

### 模块依赖关系

```text
WebSocket 回调层
    ├── ConnectionManager   （封装 WebSocket++，仅此层可见 connection_hdl）
    └── OnlineManager       （业务状态，不依赖 WebSocket++）

Matcher
    ├── OnlineManager       （状态校验与切换）
    └── BlockQueue          （匹配请求队列）

业务模块（Matcher、棋局逻辑等）
    └── 只 #include "online.hpp"，不可见 connection_hdl
```

**硬性约束**：`connection_hdl` 只允许出现在 `connection_manager.hpp` 和 WebSocket 接线层，禁止渗透到任何业务头文件。

#### 1.2 `online.hpp` 实现

```cpp
// online.hpp —— 只管在线状态与业务状态，不依赖 WebSocket++

enum class OnlineStatus {
    OFFLINE   = 0,
    HALL_IDLE = 1,
    MATCHING  = 2,
    IN_ROOM   = 3
};

class OnlineManager {
public:
    void user_online(int64_t user_id);
    void user_offline(int64_t user_id);
    bool is_online(int64_t user_id) const;

    bool set_status(int64_t user_id, OnlineStatus status);
    OnlineStatus get_status(int64_t user_id) const;

    size_t online_count() const;
};
```

**关键点**：

- 维护 `user_id -> OnlineStatus` 映射，不含任何连接句柄
- 所有访问线程安全，统一由 `mutex` 保护
- 用户离线时自动清理映射
- 与数据库 `user.status` 字段保持一致，必要时同步写库
- 明确默认行为：`user_online()` 仅标记用户在线并将状态初始化为 `HALL_IDLE`

### Phase 2-A: `connection_manager.hpp` - 连接管理模块

**交付物**: `source/include/connection_manager.hpp`, `source/tests/test_connection_manager.cpp`

#### 2-A.1 `connection_manager.hpp` 实现

```cpp
// connection_manager.hpp —— 封装 WebSocket++，唯一可见 connection_hdl 的业务文件

class ConnectionManager {
public:
    void add(int64_t user_id, connection_hdl hdl);
    void remove(int64_t user_id);
    bool get(int64_t user_id, connection_hdl& out) const;

    // 成功发送返回 true；用户不存在或连接失效返回 false
    bool send(int64_t user_id, const std::string& msg);
};
```

**关键点**：

- `connection_hdl` 只在此文件及 WebSocket 接线层可见
- WebSocket 回调层在 `on_open` 时调用 `conn_mgr.add()` + `online_mgr.user_online()`
- 断开时统一走 `handle_disconnect(user_id)`，同步清理两个管理器
- `send()` 失败语义明确：
  - 用户不存在返回 `false`
  - 连接失效返回 `false`
  - 连接失效时允许由上层统一决定是否调用 `handle_disconnect(user_id)`

```cpp
// WebSocket 接线层（示例）
void handle_disconnect(int64_t user_id) {
    conn_mgr_.remove(user_id);
    online_mgr_.user_offline(user_id);
    // 如果正在匹配，同时通知 Matcher 取消
}
```

### Phase 2-B: `block_queue.hpp` - 阻塞队列

**交付物**: `source/include/block_queue.hpp`, `source/tests/test_block_queue.cpp`

#### 2-B.1 `block_queue.hpp` 实现

```cpp
template <class T>
class BlockQueue {
public:
    // true  = 成功取到数据，out 有效
    // false = 超时 或 已 shutdown，out 无效
    //         调用方需结合 is_shutdown() 决定是否退出循环
    bool timed_pop(T& out, int timeout_ms = 100);

    void push(const T& value);
    void shutdown();
    bool is_shutdown() const;
    size_t size() const;
    bool empty() const;

    BlockQueue(const BlockQueue&) = delete;
    BlockQueue& operator=(const BlockQueue&) = delete;
};
```

#### `match_loop` 消费模式（语义约束）

```cpp
void Matcher::match_loop() {
    MatchRequest req;
    while (!queue_.is_shutdown()) {
        if (queue_.timed_pop(req, 100)) {
            process(req);
        }
        // timed_pop 返回 false 时：
        // - is_shutdown() == false -> 正常超时，继续循环
        // - is_shutdown() == true  -> 准备退出
        // 超时间隙可做懒删除条目的定期清理
    }
}
```

## Phase 3: `matcher.hpp` - 匹配器骨架与匹配算法

**计划开始**: Phase 1 + Phase 2 全部完成后  
**预计工时**: 4-6 小时  
**交付物**: `source/include/matcher.hpp`, `source/tests/test_matcher.cpp`

### 任务拆解

#### 3.1 数据结构设计

```cpp
enum class MatchTier {
    BRONZE = 0,   // 0    ~ 1299
    SILVER = 1,   // 1300 ~ 1699
    GOLD   = 2,   // 1700+
    TIER_COUNT = 3
};

// tier 不存入请求结构，由 score_to_tier() 在 enqueue() 内计算
struct MatchRequest {
    int64_t  user_id;
    int      score;
    int64_t  enqueue_time;
    uint64_t request_id;
    bool     cancelled;
};
```

#### 3.2 `matcher.hpp` 实现

```cpp
class Matcher {
public:
    void init(OnlineManager* online_mgr);

    // 入队前置条件：用户必须处于 HALL_IDLE
    // 不满足则返回 false，不做静默失败
    // 成功入队后自动将用户状态切为 MATCHING
    bool enqueue(int64_t user_id, int score);

    // 取消匹配（懒删除：打 cancelled 标记）
    bool cancel(int64_t user_id);

    // 用户断线时调用，同 cancel 语义
    void on_disconnect(int64_t user_id);

    void start();
    void stop();

private:
    static MatchTier score_to_tier(int score);

    void match_loop();
    void try_match_same_tier(int tier);
    void try_match_cross_tier(int tier);

    bool is_request_valid(const MatchRequest& req) const;
};
```

**关键实现点**：

- 入队校验：`enqueue()` 先调用 `online_mgr_->get_status()` 确认为 `HALL_IDLE`，否则返回 `false`
- `tier` 计算：`score_to_tier()` 在 `enqueue()` 内调用，结果只用于选桶，不持久化
- 出队二次校验 `is_request_valid()`：
  - 用户仍在线：`online_mgr_->is_online()`
  - 用户状态仍为 `MATCHING`
  - `cancelled == false`
- 匹配成功后生成最小房间占位信息：`room_id`、双方 `user_id`、颜色分配
- `room_id` 来源在实现前固定为一种方案：
  - 默认建议：先用内存自增生成临时 `room_id`
  - 若 M4 需要直接承接持久化房间，可切换为创建 `room` 记录后使用数据库主键

#### 3.3 测试用例 (`test_matcher.cpp`)

## Phase 4: WebSocket 事件接入与大厅前端联动

**计划开始**: Phase 3 完成后  
**预计工时**: 3-5 小时  
**交付物**: 服务端匹配事件处理、`client/hall.html`、`client/js/websocket.js`、联调记录

### 任务拆解

#### 4.1 服务端事件接入

- [ ] `match.start` - 发起匹配（JWT 校验 -> 状态校验 -> 入队）
- [ ] `match.cancel` - 取消匹配
- [ ] `ping` - 心跳请求（M3 简单处理，标注候选下沉到连接管理层）
- [ ] 返回 `match.waiting`
- [ ] 返回 `match.success`
- [ ] 返回 `error`
- [ ] 返回 `pong`

#### 4.2 事件协议约定

**客户端 -> 服务端**

```json
{ "event": "match.start",  "data": { "token": "..." } }
{ "event": "match.cancel", "data": { "token": "..." } }
{ "event": "ping",         "data": { "timestamp": 1710000000 } }
```

**服务端 -> 客户端**

```json
{ "event": "match.waiting", "data": { "queue_position": 1, "wait_time": 0 } }
{ "event": "match.success", "data": { "room_id": 1001, "opponent": { "user_id": 42, "username": "..." }, "color": "black" } }
{ "event": "error",         "data": { "code": 4001, "message": "not in hall" } }
{ "event": "pong",          "data": { "timestamp": 1710000000 } }
```

**说明**：

- `queue_position` 仅用于大厅提示，允许为近似值，不要求强一致
- `ping/pong` 在 M3 阶段继续放在 WebSocket 事件层简单处理
- 后续心跳逻辑建议迁移至 `ConnectionManager` 作为基础设施能力，避免 M4/M5 分散

#### 4.3 大厅前端实现

- [ ] 登录成功后建立 WebSocket 连接，token 随事件携带

## 五、风险与应对

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|----------|
| WebSocket 状态与在线表不一致 | 中 | 高 | 统一封装 `handle_disconnect()`，禁止散乱调用 |
| 并发下重复匹配 | 中 | 高 | 出队前二次校验 + 用户状态校验 |
| 取消匹配逻辑复杂 | 中 | 中 | 懒删除，降低队列删除复杂度 |
| 匹配线程无法优雅退出 | 低 | 中 | `BlockQueue::shutdown()` 保证消费线程可退出 |
| 前端状态残留 | 中 | 中 | 大厅页统一维护 `idle / matching / matched` 三态 |
| `connection_hdl` 依赖渗透 | 低 | 高 | Code Review 检查业务头文件，架构约束验收项兜底 |

## 三、技术方案详解

### 3.1 Logger 模块设计

#### 架构图

```
┌─────────────────────────────────────────────────────────┐
│                    业务线程                              │
│  LOG_INFO("msg") → 锁内判断 → 队列 push                  │
└─────────────────────────────────────────────────────────┘
                           │
                           │ std::condition_variable
                           ▼
┌─────────────────────────────────────────────────────────┐
│                   后台写入线程                           │
│  队列 pop → 批量写入 → 日志轮转检查 → flush             │
└─────────────────────────────────────────────────────────┘
```

#### 核心特性

| 特性 | 实现 | 收益 |
|------|------|------|
| 单例模式 | `static Logger inst` | 全局唯一实例 |
| 异步写入 | 后台线程消费队列 | 业务线程不阻塞 |
| 容量上限 | 10000 条，锁内判断 | 防止内存爆炸 |
| 日志轮转 | `stat()` 检查文件大小 | 自动备份旧日志 |
| 宏封装 | `LOG_INFO("msg" << val)` | 调用简洁 |
| 文件名提取 | `strrchr()` 提取文件名 | 日志更清爽 |

#### 关键代码

```cpp
// 容量上限检查（锁内，避免数据竞争）
void log(LogLevel level, const std::string& msg, const char* file, int line) {
    if (level < _min_level) return;

    std::string entry = _format(level, msg, file, line);

    {
        std::lock_guard<std::mutex> lk(_mtx);
        if (_queue.size() >= MAX_QUEUE_SIZE && level < LogLevel::ERROR) {
            _drop_count++;
            return;
        }
        _queue.push(std::move(entry));
    }
    _cv.notify_one();
}
```

### 3.2 Util 模块设计

#### 命名空间层次

```
gobang::
├── util::
│   ├── json_to_str()
│   ├── str_to_json()
│   ├── make_response()
│   ├── now_sec()
│   ├── format_time()
│   ├── trim()
│   ├── split()
│   ├── valid_username()
│   ├── board_to_str()
│   ├── str_to_board()
│   ├── Config (struct)
│   ├── load_config()
│   └── validate_config()
└── util::detail::
    └── _parse_line()  // 内部函数，不公开
```

#### 设计原则

| 原则 | 实践 |
|------|------|
| Header-only | 全部 `inline`，无需 `.cpp` |
| 细节隔离 | 内部函数放入 `detail` 命名空间 |
| 零依赖 | 仅依赖标准库 + JsonCpp |
| 跨平台 | Windows/Linux 兼容（`#ifdef _WIN32`） |

### 3.3 配置文件设计

#### INI 格式选择

选择 `key = value` 格式而非 JSON/YAML：

```ini
# 注释清晰
server_port = 8080
db_password = yourpassword  # 行内注释也支持
```

**理由**:
- 手写不容易出错
- 支持注释（`#`开头）
- 解析器实现简单

#### 校验规则

| 参数 | 校验规则 |
|------|----------|
| `db_password` | 不能为空 |
| `server_port` | 1-65535 |
| `db_pool_size` | 1-100 |
| `heartbeat_interval` | 1-300 |

## 四、问题追踪与修复

### 4.1 问题汇总

| # | 问题描述 | 严重性 | 发现阶段 | 修复耗时 |
|---|----------|--------|----------|----------|
| 1 | 缺少 `<sys/stat.h>` 头文件 | 🔴 编译错误 | 编译测试 | < 1 min |
| 2 | CMake 线程库逻辑不一致 | 🟡 代码质量 | 代码 Review | 2 min |
| 3 | `_parse_line` 暴露在公共命名空间 | 🟢 代码整洁 | 代码 Review | 5 min |
| 4 | `Config` 和 `load_config` 误放入 `detail` | 🔴 编译错误 | 编译测试 | 2 min |

### 4.2 根因分析

**问题 1：缺少头文件**
- **原因**: 设计方案中未明确列出所有需要的头文件
- **改进**: 后续新模块开发前先列出完整依赖清单

**问题 4：命名空间错误**
- **原因**: 修复问题 3 时操作过度，将公开 API 也移入 `detail`
- **改进**: 使用 `Edit` 工具时更仔细地区分内部函数和公开 API

1. **多模型交叉验证**

   - 提前发现队列容量、文件名提取等问题
   - **后续保持**: 每个重要模块开发前都进行设计 review

2. **测试先行**
   - 写完模块立即写测试
   - 7 个测试项覆盖核心功能
   - **后续保持**: M2 继续为每个模块编写测试

3. **详细注释**
   - 代码注释清晰，方便后续维护
   - 函数用途、参数说明、使用示例齐全
   - **后续保持**: 业务模块继续保持

4. **错误修复迅速**
   - 编译错误当天发现当天修
   - 不拖延，不累积技术债务
   - **后续保持**: 持续快速响应

### 6.2 需要改进的地方

1. **Windows 兼容性测试不足**
   - `<sys/stat.h>` 在 Windows 下路径不同
   - 虽然有 `#ifdef _WIN32`，但未实际测试

2. **本地测试环境缺失**
   - 依赖用户在 Linux 环境编译
   - 本地无法快速验证修改是否正确

3. **文档滞后**
